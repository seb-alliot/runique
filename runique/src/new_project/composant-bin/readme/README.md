# {{PROJECT_NAME}}

A web application built with [Runique](https://runique.io/docs/en), generated by
`runique new` (Runique v{{RUNIQUE_VERSION}}).

## Quick start

```bash
# 1. Create the framework's tables (accounts, sessions, rights)
runique migration up

# 2. Run the application
cargo run
```

Then open **http://127.0.0.1:3000**. The project comes with sign up, sign in
and sign out.

The first `runique migration up` compiles the `migration` crate, so it takes a
little while; later runs are quick.

## Your own models

Declare each model in its own file under `src/entities/`, with `model!`:

```rust
// src/entities/article.rs
use runique::prelude::*;

model! {
    Article,
    table: "articles",
    pk: id => Pk,
    {
        title:      text     [required, max_length: 150],
        body:       textarea [required],
        created_at: datetime [auto_now],
    }
}
```

List it in `src/entities/mod.rs` (`pub mod article;`), then:

```bash
runique makemigrations   # compares the models to their snapshots, writes the migration
runique migration up     # applies it
```

To change a model later, edit it and run the same two commands: `makemigrations`
writes an `ALTER` migration. A destructive change (dropped column, shorter
length, `nullable` to required...) is blocked unless you pass `--force`.

> **Changing a column's type is not supported yet.** `makemigrations` blocks it;
> with `--force`, the migration it writes holds only a warning comment, no
> `ALTER`, while the snapshot already records the new type. The migration then
> "applies" without touching the database, and nothing tells you afterwards.
> Until it is supported: write that migration's `up()` and `down()` by hand
> (SeaORM's `alter_table` / `modify_column`) before running `migration up`, or
> add a new column, copy the data over, then drop the old one.

## Migrations

| Command | What it does |
|---|---|
| `runique makemigrations` | Writes the migrations for the models that changed |
| `runique makemigrations --force` | Same, allowing destructive changes |
| `runique migration up` | Applies every pending migration |
| `runique migration down -n 1` | Rolls back the last migration (its `down()` runs) |
| `runique migration status` | Lists the migrations and whether each one is applied |

`migration/` is a standard SeaORM migration crate: `makemigrations` keeps its
`src/lib.rs` up to date, there is nothing to write in it by hand. The
`runique migration` commands run it for you and read `DATABASE_URL` from `.env`.

## Versions

Runique v{{RUNIQUE_VERSION}} is built with SeaORM `{{SEA_ORM_REQ}}`: `Cargo.toml` and
`migration/Cargo.toml` pin that exact version. Don't change it by hand; when you
upgrade Runique, update both files to the version the new release uses.

## Configuration

`.env` holds the settings: `IP_SERVER` and `PORT` (where the server listens),
`DEBUG`, `SECRET_KEY` (generated for this project: keep it secret, set a new one
per deployment) and the database (`DB_ENGINE`, `DATABASE_URL`).

To use PostgreSQL or MySQL instead of SQLite, change all three together: the
`runique` feature in `Cargo.toml` and in `migration/Cargo.toml` (with the
matching `sqlx-postgres` / `sqlx-mysql` feature of `sea-orm-migration`), and
`DB_ENGINE` / `DATABASE_URL` in `.env`.

## Going further

- Password reset by email: `.with_password_reset(...)` on the builder, with a mailer.
- Admin panel: the `admin` feature of `runique`, then `.with_admin(...)`.

Both are described in the documentation: **https://runique.io/docs/en**

## Troubleshooting

- **"no such table"**: the migrations aren't applied yet. Run `runique migration up`.
- **Port 3000 already in use**: change `PORT` in `.env`.
- **The database isn't found**: run `cargo run` and `runique migration` from the
  project root, where `.env` is; a relative SQLite path is read from there.
