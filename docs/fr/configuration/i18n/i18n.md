# Internationalisation (i18n)

Runique intègre un système d'internationalisation léger, sans dépendance externe.
Les traductions sont embarquées à la compilation sous forme de fichiers JSON, et la langue active est un état global modifiable à l'exécution.

---

## Langues supportées

| Variante `Lang` | Code | Exemples de locales reconnues |
| --- | --- | --- |
| `Lang::Fr` | `fr` | `fr`, `fr-FR`, `fr-CA`, `fr-BE`, `fr-CH` |
| `Lang::En` | `en` | `en`, `en-US`, `en-GB`, `en-CA` |
| `Lang::De` | `de` | `de`, `de-DE`, `de-AT`, `de-CH` |
| `Lang::Es` | `es` | `es`, `es-ES`, `es-MX`, `es-AR`, `es-CO`, `es-CL` |
| `Lang::It` | `it` | `it`, `it-IT`, `it-CH` |
| `Lang::Pt` | `pt` | `pt`, `pt-PT`, `pt-BR` |
| `Lang::Ja` | `ja` | `ja`, `ja-JP` |
| `Lang::Zh` | `zh` | `zh`, `zh-CN`, `zh-TW`, `zh-HK` |
| `Lang::Ru` | `ru` | `ru`, `ru-RU`, `ru-BY`, `ru-UA` |

Les variantes de la dernière colonne sont des exemples : toute variante régionale est reconnue comme sa langue (`fr-LU` est `fr`), seule la première partie du code compte.

La langue par défaut est `Lang::En` si aucune configuration explicite n'est fournie.

---

## API disponible

```rust
use runique::translation::{current_lang, t, tf, Lang};

// Lire la langue en cours
let lang = current_lang(); // → Lang::Fr si le site est en français

// Traduire une clé
let msg = t("forms.error.required"); // → "Ce champ est obligatoire"

// Traduire une clé avec paramètres (remplace {} par les arguments)
let msg = tf("forms.error.too_short", &[3]); // → "Trop court (min 3)"
```

| Fonction | Signature | Description |
| --- | --- | --- |
| `current_lang` | `fn current_lang() -> Lang` | La langue en cours : celle du visiteur si le site suit son navigateur, sinon celle du site |
| `t` | `fn t(key: &str) -> Cow<'static, str>` | Traduit une clé simple |
| `tf` | `fn tf<T: Display>(key: &str, args: &[T]) -> String` | Traduit une clé avec substitutions `{}` |
| `Lang::find` | `fn find(code: &str) -> Option<Lang>` | La langue d'un code (`"fr"`, `"fr-FR"`), ou rien si aucune langue chargée n'y répond |

La langue du site se choisit par le `.env` ou par le builder, voir [Choisir la langue](#choisir-la-langue).

---

## Format des clés

Une clé s'écrit `sujet.nature.clé`. Le sujet est le nom du fichier, la nature une section de ce fichier.

```text
forms.error.required     → locales/<langue>/forms.json   { "error": { "required": "…" } }
forms.hint.slug          → locales/<langue>/forms.json   { "hint":  { "slug": "…" } }
admin.login.label.title  → locales/<langue>/admin/login.json   { "label": { "title": "…" } }
```

Les natures : `error` (un refus ou un échec), `label` (titres, boutons, libellés), `hint` (une aide), `log` (une ligne de journal), `info` (ce qui vient de se passer).

Chaque clé de Runique a sa constante, qui suit le même chemin :

```rust
use runique::translation::{keys, t, tf};

t(keys::forms::error::REQUIRED);            // « Ce champ est obligatoire »
tf(keys::forms::error::TOO_SHORT, &[3]);    // « Trop court (min 3) »
```

Une constante mal écrite ne compile pas. Le `{}` dans un texte est remplacé, dans l'ordre, par les arguments passés à `tf`.

---

## Comportement de repli

Pour une clé, Runique cherche dans cet ordre :

1. les fichiers du projet pour la langue en cours (voir plus bas) ;
2. les fichiers de Runique pour cette langue ;
3. la langue de repli de cette langue, de la même façon, jusqu'à l'anglais ;
4. si rien ne l'a, la clé elle-même.

Une traduction incomplète ne provoque donc jamais de panique.

## Les traductions du projet : le dossier `locales/`

Un projet range ses propres traductions dans un dossier `locales/` à sa racine, organisé comme celui de Runique : un dossier par langue, un fichier par sujet.

```text
mon_projet/locales/
├── fr/
│   ├── boutique.json      ← un sujet du projet
│   └── forms.json         ← des messages de Runique réécrits
└── nl/                    ← une langue que Runique n'a pas
    ├── lang.json
    └── forms.json
```

Runique lit ce dossier au démarrage, l'application comme la commande `runique`. Aucun code à écrire.

**Traduire son site.** Un fichier qui ne porte pas le nom d'un sujet de Runique est un sujet du projet :

```json
// locales/fr/boutique.json
{ "titre": "Boutique", "panier": { "vide": "Votre panier est vide" } }
```

```rust
t("boutique.titre");
t("boutique.panier.vide");
```

**Réécrire un message de Runique.** Un fichier du nom d'un sujet de Runique, avec la même clé : le message du projet passe devant, pour cette langue seulement.

```json
// locales/fr/forms.json
{ "error": { "required": "À remplir" } }
```

**Ajouter une langue.** Un dossier dont le nom n'est pas une langue de Runique en est une nouvelle. Son nom est le code de la langue, `nl`. Un dossier `nl-NL` ou `nl_NL` est accepté et donne la même langue `nl` ; deux dossiers pour une même langue (`nl-NL` et `nl-BE`) arrêtent le démarrage. Un dossier `pt-BR` n'ajoute pas de langue : il complète le portugais de Runique. Un fichier `lang.json` décrit la langue :

```json
// locales/nl/lang.json
{ "name": "Nederlands", "fallback": "fr" }
```

| Champ | Rôle | Sans lui |
|---|---|---|
| `name` | le nom de la langue | son code |
| `aliases` | un autre nom pour la langue, cherché tel qu'il est écrit (`dutch`) ; inutile pour les variantes régionales, déjà reconnues | aucun |
| `fallback` | la langue où chercher un message qui manque | l'anglais |

Une langue du projet n'a pas besoin de tout traduire : ce qui manque s'affiche dans sa langue de repli. Elle s'obtient par son code :

```rust
let neerlandais = Lang::from("nl");
```

**Ce que Runique vérifie au démarrage.**

| Cas | Ce qui se passe |
|---|---|
| un fichier JSON invalide, ou une valeur qui n'est ni un texte ni une section | le démarrage s'arrête, avec le nom du fichier |
| un dossier dont le nom n'est pas un code de langue | le démarrage s'arrête |
| une langue de repli inconnue, ou des replis qui tournent en rond | le démarrage s'arrête |
| deux dossiers pour la même langue, ou deux langues sous le même alias | le démarrage s'arrête |
| une clé inconnue de Runique dans un de ses sujets (`forms.error.requird`) | un avertissement au journal : presque toujours une faute de frappe |
| un message réécrit avec un autre nombre de `{}` | un avertissement au journal |
| des messages de Runique non traduits dans une langue nouvelle | un bilan par sujet au journal |

Le dossier se range ailleurs avec `LOCALES_DIR` dans le `.env`.

## Choisir la langue

Par le `.env`, à la racine du projet :

```ini
LANG=fr
```

ou dans le builder, pour l'imposer depuis le code :

```rust
RuniqueAppBuilder::new(config)
    .with_lang("fr")
```

Le builder a le dernier mot sur le `.env`. Sans l'un ni l'autre, le site est en anglais.

| | L'application | La commande `runique` |
|---|---|---|
| `.with_lang("fr")` du builder | oui, il a le dernier mot | sans objet |
| `LANG` du `.env` | oui | oui, en premier |
| `LANG` du système | non : la langue d'un serveur n'est pas celle du site qu'il sert | oui, ensuite |

**Un code, une langue.** Seule la première partie d'un code compte : `fr`, `fr-FR`, `fr_FR.UTF-8` et `fr-LU` sont tous le français, `pt-BR` et `pt-PT` le portugais. Vous voulez du portugais, vous écrivez `pt`, quel que soit le pays.

**Un code que personne ne porte.** Dans `.with_lang("xx")`, il arrête le démarrage, avec la liste des langues chargées : une faute de frappe ne passe pas en silence. Dans le `.env`, il donne l'anglais. `LC_ALL` et `LC_MESSAGES` y sont lues comme `LANG`.

Sans rien de plus, la langue est la même pour tous les visiteurs.

## La langue de chaque visiteur : `.with_lang()` des middlewares

```rust
RuniqueAppBuilder::new(config)
    .with_lang("fr")                  // la langue du site
    .middleware(|m| m.with_lang())    // et il suit le navigateur de chaque visiteur
```

Les deux portent le même nom à deux niveaux : sur le builder, `.with_lang("fr")` fixe la langue du site ; dans les middlewares, `.with_lang()` autorise à en changer pour chaque visiteur.

Chaque visiteur est alors servi dans la langue de son navigateur. Le navigateur envoie ses langues par ordre de préférence dans l'en-tête `Accept-Language` ; Runique prend la première qu'il a, parmi les siennes et celles du dossier `locales/` du projet. S'il n'en a aucune, la langue du site reste.

Pour un site qui a le français, l'anglais et un dossier `locales/nl/`, en français par défaut :

| Le navigateur envoie | Le visiteur voit |
|---|---|
| `nl-BE, fr;q=0.8` | le néerlandais |
| `sv, en;q=0.8, fr;q=0.5` | l'anglais : le suédois n'existe pas, le suivant oui |
| `fr-LU` | le français : une variante régionale compte comme sa langue |
| `sv, da` | le français, langue du site |
| rien (un robot) | le français, langue du site |

Tout suit, sans rien changer au code : `t()`, `tf()`, les erreurs de formulaire, les pages d'erreur, l'administration. Dans un template, `{{ lang }}` donne le code de la langue servie :

```html
<html lang="{{ lang }}">
```

Cet attribut compte : c'est lui que lit le navigateur pour proposer au visiteur de traduire une page qui n'est pas dans sa langue.

À savoir :

* La langue vaut pour la requête. Une tâche lancée à part (`tokio::spawn`) retrouve la langue du site.
* Chaque réponse porte `Vary: Accept-Language` : un cache placé devant l'application ne sert pas une page française à qui demande l'anglais.
* L'en-tête est une entrée du visiteur : il ne fait que choisir parmi les langues chargées, et n'est jamais réécrit dans la réponse.
* Le visiteur ne choisit pas sa langue sur le site : elle suit les réglages de son navigateur.
