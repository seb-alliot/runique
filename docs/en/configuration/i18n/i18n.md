# Internationalisation (i18n)

Runique includes a lightweight i18n system with no external dependencies.
Translations are embedded at compile time as JSON files, and the active language is a global state that can be changed at runtime.

---

## Supported languages

| `Lang` variant | Code | Recognised locale examples |
| --- | --- | --- |
| `Lang::Fr` | `fr` | `fr`, `fr-FR`, `fr-CA`, `fr-BE`, `fr-CH` |
| `Lang::En` | `en` | `en`, `en-US`, `en-GB`, `en-CA` |
| `Lang::De` | `de` | `de`, `de-DE`, `de-AT`, `de-CH` |
| `Lang::Es` | `es` | `es`, `es-ES`, `es-MX`, `es-AR`, `es-CO`, `es-CL` |
| `Lang::It` | `it` | `it`, `it-IT`, `it-CH` |
| `Lang::Pt` | `pt` | `pt`, `pt-PT`, `pt-BR` |
| `Lang::Ja` | `ja` | `ja`, `ja-JP` |
| `Lang::Zh` | `zh` | `zh`, `zh-CN`, `zh-TW`, `zh-HK` |
| `Lang::Ru` | `ru` | `ru`, `ru-RU`, `ru-BY`, `ru-UA` |

The variants of the last column are examples: any regional variant is recognised as its language (`fr-LU` is `fr`), only the first part of the code counts.

The default language is `Lang::En` when no explicit configuration is provided.

## Available API

```rust
use runique::utils::trad::{current_lang, t, tf, Lang};

// Read the language in use
let lang = current_lang(); // → Lang::Fr when the site is in French

// Translate a key
let msg = t("forms.error.required"); // → "This field is required"

// Translate a key with parameters (replaces {} with arguments)
let msg = tf("forms.error.too_short", &[3]); // → "Too short (min 3)"
```

| Function | Signature | Description |
| --- | --- | --- |
| `current_lang` | `fn current_lang() -> Lang` | The language in use: the visitor's when the site follows their browser, else the site's |
| `t` | `fn t(key: &str) -> Cow<'static, str>` | Translates a simple key |
| `tf` | `fn tf<T: Display>(key: &str, args: &[T]) -> String` | Translates a key with `{}` substitutions |
| `Lang::find` | `fn find(code: &str) -> Option<Lang>` | The language of a code (`"fr"`, `"fr-FR"`), or nothing when no loaded language answers to it |

The site's language is chosen through the `.env` or the builder, see [Choosing the language](#choosing-the-language).

---

## Key format

A key is written `subject.section.key`. The subject is the name of the file, the section a part of that file.

```text
forms.error.required     → locales/<language>/forms.json   { "error": { "required": "…" } }
forms.hint.slug          → locales/<language>/forms.json   { "hint":  { "slug": "…" } }
admin.login.label.title  → locales/<language>/admin/login.json   { "label": { "title": "…" } }
```

The sections: `error` (a refusal or a failure), `label` (titles, buttons, labels), `hint` (a help), `log` (a log line), `info` (what just happened).

Each of Runique's keys has its constant, which follows the same path:

```rust
use runique::utils::trad::{keys, t, tf};

t(keys::forms::error::REQUIRED);            // "This field is required"
tf(keys::forms::error::TOO_SHORT, &[3]);    // "Too short (min 3)"
```

A misspelt constant doesn't compile. The `{}` in a text is replaced, in order, by the arguments given to `tf`.

---

## Fallback behaviour

For a key, Runique looks in this order:

1. the project's files for the language in use (see below);
2. Runique's files for that language;
3. the language that one falls back on, the same way, down to English;
4. if nothing has it, the key itself.

An incomplete translation therefore never causes a panic.

## The project's translations: the `locales/` folder

A project keeps its own translations in a `locales/` folder at its root, laid out as Runique's: one folder per language, one file per subject.

```text
my_project/locales/
├── fr/
│   ├── shop.json          ← a subject of the project
│   └── forms.json         ← messages of Runique rewritten
└── nl/                    ← a language Runique doesn't ship
    ├── lang.json
    └── forms.json
```

Runique reads this folder at start, the application as well as the `runique` command. No code to write.

**Translating your site.** A file that isn't named after one of Runique's subjects is a subject of the project:

```json
// locales/en/shop.json
{ "title": "Shop", "cart": { "empty": "Your cart is empty" } }
```

```rust
t("shop.title");
t("shop.cart.empty");
```

**Rewriting a message of Runique.** A file named after one of Runique's subjects, with the same key: the project's message comes first, for that language only.

```json
// locales/en/forms.json
{ "error": { "required": "Please fill this in" } }
```

**Adding a language.** A folder whose name isn't one of Runique's languages is a new one. Its name is the code of the language, `nl`. A `nl-NL` or `nl_NL` folder is accepted and gives the same language `nl`; two folders for one language (`nl-NL` and `nl-BE`) stop the start. A `pt-BR` folder adds no language: it completes Runique's Portuguese. A `lang.json` file describes the language:

```json
// locales/nl/lang.json
{ "name": "Nederlands", "fallback": "fr" }
```

| Field | Role | Without it |
|---|---|---|
| `name` | the name of the language | its code |
| `aliases` | another name for the language, looked for as written (`dutch`); useless for regional variants, already recognised | none |
| `fallback` | the language to look in for a missing message | English |

A project's language doesn't have to translate everything: what is missing is shown in the language it falls back on. It is obtained by its code:

```rust
let dutch = Lang::from("nl");
```

**What Runique checks at start.**

| Case | What happens |
|---|---|
| an invalid JSON file, or a value that is neither a text nor a section | the start stops, with the name of the file |
| a folder whose name isn't a language code | the start stops |
| an unknown fallback language, or fallbacks going round in a circle | the start stops |
| two folders for the same language, or two languages under the same alias | the start stops |
| a key Runique doesn't know in one of its subjects (`forms.error.requird`) | a warning in the log: almost always a typo |
| a message rewritten with another number of `{}` | a warning in the log |
| messages of Runique not translated in a new language | a summary by subject in the log |

The folder is kept elsewhere with `LOCALES_DIR` in the `.env`.

## Choosing the language

Through the `.env`, at the project root:

```ini
LANG=fr
```

or in the builder, to set it from the code:

```rust
RuniqueAppBuilder::new(config)
    .with_lang("fr")
```

The builder has the last word over the `.env`. Without either, the site is in English.

| | The application | The `runique` command |
|---|---|---|
| `.with_lang("fr")` of the builder | yes, it has the last word | not applicable |
| `LANG` of the `.env` | yes | yes, first |
| `LANG` of the system | no: a server's language isn't that of the site it serves | yes, next |

**One code, one language.** Only the first part of a code counts: `fr`, `fr-FR`, `fr_FR.UTF-8` and `fr-LU` are all French, `pt-BR` and `pt-PT` Portuguese. You want Portuguese, you write `pt`, whatever the country.

**A code nobody carries.** In `.with_lang("xx")`, it stops the start, with the list of the loaded languages: a typo doesn't go unnoticed. In the `.env`, it gives English. `LC_ALL` and `LC_MESSAGES` are read there like `LANG`.

With nothing more, the language is the same for every visitor.

## Each visitor's language: the middlewares' `.with_lang()`

```rust
RuniqueAppBuilder::new(config)
    .with_lang("fr")                  // the language of the site
    .middleware(|m| m.with_lang())    // and it follows each visitor's browser
```

Both carry the same name at two levels: on the builder, `.with_lang("fr")` sets the language of the site; in the middlewares, `.with_lang()` allows it to change for each visitor.

Each visitor is then served in the language of their browser. The browser sends its languages in order of preference in the `Accept-Language` header; Runique takes the first one it has, among its own and those of the project's `locales/` folder. If it has none, the site's language stays.

For a site that has French, English and a `locales/nl/` folder, in French by default:

| The browser sends | The visitor sees |
|---|---|
| `nl-BE, fr;q=0.8` | Dutch |
| `sv, en;q=0.8, fr;q=0.5` | English: Swedish doesn't exist, the next one does |
| `fr-LU` | French: a regional variant counts as its language |
| `sv, da` | French, the site's language |
| nothing (a robot) | French, the site's language |

Everything follows, with no change to the code: `t()`, `tf()`, form errors, error pages, the admin. In a template, `{{ lang }}` gives the code of the language served:

```html
<html lang="{{ lang }}">
```

This attribute matters: it is what the browser reads to offer the visitor a translation of a page that isn't in their language.

Good to know:

* The language holds for the request. A task started apart (`tokio::spawn`) is back to the site's language.
* Every answer carries `Vary: Accept-Language`: a cache in front of the application doesn't serve a French page to someone asking for English.
* The header is a visitor's input: it only picks among the loaded languages, and is never written back in the answer.
* The visitor doesn't choose their language on the site: it follows the settings of their browser.
